# Spotter audit, October 2026: design, security, speed

_Date: 2026-10-24. Scope: the Android app, the website (`web/`), the Supabase backend
(`supabase/migrations/`) and the repository setup (CI, docs, tooling). State audited:
commit 8a409f1 plus 7178dc4 (app password accounts) and aefc572 (scheduled workouts) on the
`web-dashboard` branch, with 0.10.0 (versionCode 3) in Play review and 0.10.1 (vc 4) built and
held._

## What was audited and how

Three read-only sweeps over the whole repository, one per axis, plus the Supabase advisors:

| Axis | Question | How |
|---|---|---|
| **Design** | Is it one product? Same names, formats, spacing and states on the app and the website; easy to understand. | Inventory of every screen and page: strings, number/date formats, components, loading/empty/error states, accessibility semantics. The Android app is the source of truth; the website adopts its names. |
| **Security** | Can anyone get into someone else's account or data, or write where they shouldn't? | Inventory of every trust boundary: auth flows and deep links, RLS policies and grants, `push_rows`, server actions and routes, error text shown to users, CSP, secrets in the repo and build. |
| **Speed and quality** | Fast on phone and web, no bloat, no dead code or shortcuts in code that runs? | Inventory of every data read and write (Room DAOs, sync, Supabase views, web `data.ts`), startup work, Compose recomposition, bundle contents, dead code. |
| **Backend health** | What does Supabase itself flag? | Security and performance advisors on project `gaherwthntdonrsuowbh` (2026-10-24): WARN on the two intentional SECURITY DEFINER functions (`push_rows`, `delete_my_account`), WARN leaked-password protection off (Pro feature), WARN `auth.uid()` re-evaluated per row in all four `sync_rows` policies, INFO two unused indexes. ## Key findings

In order of weight.

1. **A crafted sign-in link could sign a phone into someone else's account.** The app installed
   Supabase Auth with the default *implicit* flow: the emailed link carried the session itself
   in the URL fragment (`spotter://login#access_token=…&refresh_token=…`), and
   `handleDeeplinks` imported whatever session a `spotter://login` link handed it. Anyone able
   to get a link opened on the phone (a message, a web page, another app, since any app may
   register the custom scheme) could put their own session on it. The first sync after that
   would then push the phone's training data into the attacker's account. **Fix: PKCE.** The app
   keeps a secret per sign-in attempt and the link carries only a one-time `code` that is
   useless without it, so the link works on the phone that asked and nowhere else; the code
   typed from the email keeps working anywhere. Fragment-only links are ignored, and the first
   sync after a link sign-in into an empty account asks before uploading. The website already
   used PKCE. https App Links (which also stop other apps from receiving the link) wait for a
   public domain.
2. **`push_rows` accepted more than it should.** It checked the table allow-list, row count and
   row size, but not that `payload` is a JSON object, that `updated_at` is plausible (a far-future
   timestamp wins every last-write-wins conflict forever), that a batch has no duplicate
   `(table_name, sync_id)`, or how many rows one user may hold in total. Also: `anon` still had
   `select` on `sync_rows` (RLS kept it empty, but the grant should not exist), and
   `truncate`/`references`/`trigger` were granted by default. Fix: additive checks in a new
   migration, same signature, compatible with 0.10.x.
3. **Raw backend error text reached users.** Web server actions and `auth.ts` returned
   `(e as Error).message` and Supabase's own messages; the web `error.tsx` showed
   `error.message`. These leak implementation detail and read badly. Fix: fixed friendly messages
   per case, matching the app's wording, with codes logged server-side.
4. **Smaller web-security gaps.** `safeNext` let `/\t/evil.com` and `/\\evil.com` through; the
   auth callback didn't validate `type`; `/reset-password` was reachable with any session;
   `deleteAccount` had no confirmation and no `requireUser()` first; the export route had no
   `Cache-Control: no-store` and included `user_id`; the middleware matcher skipped any path
   ending in an image extension; the CSP allowed `'unsafe-inline'` scripts.
5. **Design drift between app and web.** The website had its own goal names ("Deload" vs the
   app's "Lighter week", "BW" vs "Bodyweight"), guessed equipment labels, raw enum names for
   progression reasons, three copies of the PR formatter with different output, four chip
   implementations, inline `← Back` links, no focus rings, no dialog primitive, icon-only
   buttons without names and no 404/global error pages. The app had its own duplicates: three
   `RecordsCard`s, three segmented controls, hand-written empty states, hard-coded `"RIR $rir"`
   strings, per-module `cancel`/`back` strings, screens that render blank while loading, and
   destructive actions without confirmation.
6. **Data over-fetching.** Every web page loaded a user's full history (`getSessions()`,
   `getPersonalRecords()` with no filters) and filtered in memory; `/plans/[id]` fetched every
   plan; `getClaims` ran twice per request; zod shipped to the browser via `sync-writer.ts`.
   On the phone: no `updatedAt` indexes on the 11 synced tables (every incremental sync scans
   them), per-exercise query loops in `WorkoutRepository`, `NOT IN` subqueries, repositories
   reading a table twice for one value, pull pages held in memory all at once.
7. **Startup work on every launch.** `CREATE TRIGGER IF NOT EXISTS` ran on every database open,
   the exercise seeder parsed the JSON catalog before checking the stored version, the
   recommendation engine refreshed on every start, and the Supabase client was built on the
   main thread during injection.
8. **Setup.** CI ran unit tests and a debug build only (no lint, no screenshot tests, no R8
   build), used floating action tags, and had default (write) token permissions; a 3.9 MB
   review recording was committed; the server's migration history was empty because every
   migration had been pasted into the SQL editor.

## What this pass changes, per area

Plain-words summary; the per-item checklist with status is in "Result" at the end. Other
agents' code changes are described here as planned; the reviewer confirms them.

**A — Backend and web security.** A new idempotent migration rewrites the `sync_rows` policies
with `(select auth.uid())`, hardens `push_rows` (object payloads, bounded `updated_at`, no
duplicate ids in a batch, a per-user row cap, same signature and allow-list), revokes the stray
grants, makes `delete_my_account()` delete `sync_rows` explicitly before the user, and marks the
old migrations as superseded so re-running them can't downgrade `push_rows`. On the web:
stricter `safeNext`, validated callback `type`, a short-lived recovery cookie that
`/reset-password` requires, `deleteAccount` behind `requireUser()` and a typed confirmation,
fixed friendly error messages everywhere (zod included), `no-store` and a compact,
`user_id`-free export, a narrower middleware matcher, and a nonce-based CSP if Next 15.5 allows
it. Tests for each rejection case, plus a SQL test file for `push_rows`.

**B — Web pages, design and speed.** A real design system: `Field`, `Chip`, `BackLink`,
`Dialog`, `InlineMessage`, `IconButton`, focus rings, consistent tokens in light and dark, a
mobile nav that mirrors the app's tab order, `not-found` and `global-error` pages. The app's
words and formats everywhere through one `labels.ts` and one `formatSet`/`formatRecord`
("Lighter week", "Bodyweight", "80 kg × 8", "10 kg × 45 s", the app's progression sentences).
Confirmations before losing data, empty states, names on icon-only controls, one locale for
dates and numbers. Every page loads only what it shows (parameterised reads by range, month or
id, keyset "Load more" on history, server-side PR filtering), streaming shells, zod out of the
client bundle, dead code removed.

**C — Android data, sync and startup.** PKCE in `install(Auth)` and a test that fragment-only
links are ignored; the first sync after a link sign-in asks before uploading to an empty
account (showing the email); remote payloads can't carry an autoincrement `id` or overwrite a
seeded catalog exercise; the auth session is stored encrypted; the debug demo-data receiver is
closed to other apps; sync failures are logged and cancellation is rethrown. Room schema bump
with `updatedAt` indexes on every synced table and the other missing indexes; triggers created
once in a `RoomDatabase.Callback`; the seeder checks the version before parsing; recommendations
refresh at most daily; the Supabase client is built off the main thread; heavy repository work
moves to `Dispatchers.Default`; DAOs get ranged/limited queries and set-based updates instead
of per-exercise loops; sync work is no longer cancelled by its own re-scheduling and backs off
exponentially. Units: the preference writes `user_profile.units` and mirrors it back on sync.
Unused dependencies dropped; `versionCode 5`, `versionName 0.11.0`.

**D — Android UI design and performance.** Spacing, shape and size tokens; shared `SpotterTopBar`,
buttons, `SectionHeader`, `StatTile`, `RecordsCard`, `SegmentedChoice`, `LoadingState`,
`ErrorState`, `ConfirmDialog`, `SupersetBadge`; the duplicates in `feature/*` replaced with them.
Every screen shows `LoadingState` instead of blank; error feedback for sign-out, account deletion
and invalid weight; confirmations for removing an exercise and rebuilding a plan, undo snackbar
for deleting a set. Every user-facing literal moves to resources with plurals; dates use
locale-aware formatters. Accessibility: roles and click labels on rows, selection semantics in
the picker, calendar cells that announce their value, contrast fixes, warnings in tertiary
tones. Compose performance: immutable action holders, keypad state only on the focused card,
debounced writes to Room, `remember`/`derivedStateOf` where lists are recomputed per frame,
keys on lazy items, single plan subscriptions. Screenshot goldens for every screen in light,
dark, large text and dynamic colour.

**E — Setup, CI and docs (this document's author).** CI: read-only token, every action pinned to
a commit SHA, the Android job now runs unit tests, Roborazzi verification, `lintRelease`,
`assembleDebug` and a debug-signed `assembleRelease` (R8 proof), and uploads screenshot diffs
and lint reports when it fails; the web job runs a visible, non-blocking `npm audit` on
production dependencies. Docs: this record; PKCE, App Links, units and migration handling in
`infrastructure.md` and `README.md`; the 0.11.0 row and the recording note in the Play docs;
`docs/play-store/*.mp4` gitignored and the committed recording untracked (the file stays on
disk and in history); `web/.env.example` says only publishable values belong there; `README.md`
says that `.mcp.json` enables a write-capable Supabase MCP for anyone who authenticates.

### Notes for the reviewer (found while writing this)

- The plan named A's new migration `20261025000000_audit_hardening.sql`, but
  `20261025000000_scheduled_sessions.sql` already exists and is live. It is
  `20261026000000_audit_hardening.sql` instead; besides the hardening it adds `v_exercise_usage`,
  which the website's `/library` page needs, so the website must not deploy before it is
  applied. The repair command below names the four versions that are live today (the plan's
  draft left out scheduled sessions); `supabase db push` then applies `20261026000000`.
- The plan had C bumping Room to version 7 for the new indexes, but `7.json` already existed
  (scheduled sessions, aefc572). The schema is now version 8, and every Room migration
  re-creates the sync triggers via `SyncSchema.TriggerSpec`. `web/src/lib/sync-writer.test.ts`
  reads the newest schema file.
- As implemented in the app: `SupabaseProvider` sets `flowType = FlowType.PKCE`;
  `SignInLinks.parse` accepts only `spotter://login?code=…`; password-reset links are detected
  from the token's `amr` claim (`recovery`) with the old `type=recovery` query as fallback; the
  session lives in `EncryptedSharedPreferences` (`spotter_auth`) with a one-time migration from
  the plain store; the seeded catalog is versioned by `EXERCISE_CATALOG_VERSION` in
  `ExerciseSeeder` (bump it whenever `exercises.json` changes).
- On the web, `src/lib/labels.ts` mirrors the app's string resources (update both when wording
  changes) and the locale constant (`en-GB`) sits in `src/lib/tz.ts`.
- `actions/setup-java` marked its v4 line deprecated upstream in August 2026; v4.9.1 is pinned
  as agreed, and moving to v5 is a small follow-up. `gradle/actions`' `v4` tag resolves to
  v4.4.3 while v4.4.4 exists; the pin follows the tag.
- Roborazzi goldens were recorded on macOS; `verifyRoborazziDebug` on Linux CI can differ in
  font rasterisation. If the first CI run fails only on screenshots, re-record on CI or set a
  small tolerance in the Roborazzi options rather than disabling the task.

## Review

The reviewer's verdict on `ed6a9b5` (the merged audit branch) was **not ready**, with one
blocker and several shoulds, all addressed in the "review fixes" commits before the Result
table below was filled in:

- **Blocker:** on the web, resetting a password with the emailed *code* (not the link) bounced
  off the new recovery cookie that `/reset-password` requires, because the code path never set
  it. Fixed by Agent A in the review round.
- **Shoulds:** a guard around the encrypted session store (fall back cleanly if the keystore is
  unavailable); undo-snackbar timing for set deletion; raw `dp` literals left in `feature/**`;
  `requireUser` memoised so it runs once per request; calendar queries scoped to the month
  shown; nav grouping of the extra web pages under the app's four tabs. All addressed.

Still open after review: the production migration (M) and the dashboard checklist (DC).
